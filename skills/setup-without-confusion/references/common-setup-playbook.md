# Common setup playbook

Use the relevant section only.

## Git and GitHub

- Check whether Git is installed and the user is signed in to GitHub.
- Before publishing, inspect files for passwords, access keys, private records, personal exports, and large generated files.
- Use a private repository unless the user clearly asks for public access.
- After publishing, verify the repository's visibility and open its public page.
- Tell the user "Your project is saved on GitHub" unless technical details matter.

## Local apps and localhost

- Start the required process and test its full address.
- Explain localhost as "a preview that works only on this computer."
- If the user asked to share the result, publish it. A localhost preview does not satisfy that request.

## Accounts and sign-in

- Prefer an existing authorized account that matches the task.
- Continue through ordinary sign-in, access approval, and confirmation screens.
- Ask the user only for a step the agent cannot perform, such as a code on another device.
- Confirm which account completed the setup when identity matters.

## Secrets and helper tools

- Keep passwords, access keys, cookies, and private details out of public files, screenshots, logs, and chat.
- Store required secrets through the tool's private settings.
- Never replace or cancel a working access key unless the user asked.
- Install a helper when it clearly reduces repeated work or is required to finish the request.
- Prefer maintained, well-known sources and verify the helper works.

## Publishing

- Check the intended audience. Public means anyone with the address can view it.
- Remove secrets and private data before release.
- Verify the public URL in a signed-out or anonymous view when possible.
- Say what is public, where it lives, and whether later edits update automatically.
